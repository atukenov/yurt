# Modules: what each gate covers

Reference for the paid modules once they are gated (Phase 3 of `MODULARIZATION_TODO.md`). One module is gated per
release. A disabled module answers `403 { code: "module_disabled", module: "<key>" }`; its screens disappear from the
apps; its data is never deleted. Everything is on by default (fail-open).

How a gate is built:
1. Backend: `[RequireModule(ModuleKeys.X)]` on the controller or action (`Yurt.WebApi/Common/RequireModuleAttribute.cs`).
   Background jobs ask `IModuleGate.IsEnabledAsync` before working.
2. Frontend: `moduleGuard('key', '/fallback')` on the route and `modules.isEnabled('key')` around the menu entry.
3. Test: switching the module off through `/api/v1/platform/modules/{key}` gives `403` and switching it back on restores access.
4. Document it here.

## Gated

### `analytics` (admin only, no customer impact)
- **Covers:** `GET /api/v1/admin/analytics`, `GET /api/v1/admin/dashboard`; the admin **Analytics** page and menu entry.
- **When off:** the page redirects to Orders, the menu entry is hidden, both endpoints return `403 module_disabled`.
- **Does not cover:** the customer-report moderation page (`/admin/reports`, `ReportsController`), which belongs to `core`.
- **Depends on:** nothing.

### `marketing` (promotions and discount codes)
- **Covers:** `/api/v1/promotions/*`, `/api/v1/discount-codes/*`, `/api/v1/admin/promotions/*`, `/api/v1/admin/discount-codes/*`; the admin **Promotions** and **Discount codes** pages and menu entries; in the customer app the promo popup, the promotions strips on Menu and News, and the code field in the cart.
- **When off:** those endpoints return `403 module_disabled`, admin routes redirect to Orders, the customer UI hides the promo surfaces, and a code already applied in the cart is cleared.
- **Checkout is unaffected:** `POST /orders` ignores a `discountCode` while the module is off and creates the order at full price (no error).
- **Existing data:** promotions, codes and the discount recorded on past orders stay as they are and show again when the module is back on.
- **Depends on:** nothing.

### `group_orders` (shared carts and join links)
- **Covers:** every `/api/v1/group-orders/*` endpoint (create, join, view, add/remove item, checkout); in the customer app the `group-order/*` routes.
- **When off:** endpoints return `403 module_disabled` and the routes redirect to the cart. The "Start/Join group order" links in the cart are currently commented out in the template; when they are re-enabled they must be wrapped in `modules.isEnabled('group_orders')`.
- **Checkout is unaffected:** regular orders do not touch group carts. A group cart created before the module was turned off cannot be continued until it is back on.
- **Depends on:** nothing.

### `engagement` (ratings, achievements, 2GIS directions)
- **Covers:** `POST /api/v1/orders/{id}/rating`; in the customer app the rating card on a completed order, the achievements route, the achievements tiles on News and Profile, and the 2GIS "route" button on an accepted order; in the admin app the rating shown on an order and the 2GIS link field on a location.
- **When off:** the rating endpoint returns `403 module_disabled`, `/achievements` redirects to News, and the UI above is hidden. Achievements are computed in the app from the customer's own stats, so there is no endpoint to gate.
- **Existing data:** ratings already given and each location's stored 2GIS link are kept and show again when the module is back on. The location API still accepts and returns the 2GIS link; only the UI is hidden.
- **Depends on:** nothing.

### `staff_audit` (staff accounts and the audit log)
- **Covers:** `/api/v1/admin/workers/*` (create, edit, activate/deactivate staff accounts) and `GET /api/v1/admin/audit-log`; the admin **Staff** and **Audit log** pages and menu entries.
- **When off:** those endpoints return `403 module_disabled`, the pages redirect to Orders and the menu entries are hidden.
- **Keeps working:** existing staff accounts can still sign in and work orders (the module only covers managing accounts). The audit log keeps being written in the background so the history is complete when the module is switched back on; only reading it is gated.
- **Who sees what:** a cafe admin sees only their own cafe's history. Platform operator actions (cafes, keys, licenses, maintenance, brand, billing, fiscal and payment settings, app releases, exports) are written with `IsPlatform` and only SuperAdmins see them: the operator's Audit log opens on **Platform actions** (all cafes, `scope=platform`) and can pick one cafe to see that cafe's own history (`scope=cafe` + `X-Tenant`). New platform-only actions must use `IAuditLogService.LogPlatformAsync`.
- **Depends on:** nothing.

### `multi_location` (more than one branch)
- **Core includes one location.** This is the only module that limits instead of blocking a feature, because locations are part of ordering.
- **When off:** `POST /api/v1/admin/locations` returns `403 module_disabled` once one location exists; the admin **Add location** button is replaced by a note; `GET /api/v1/locations` (customer app) returns only the first active location (by name).
- **Kept working:** viewing and editing locations, working hours, the closed notice, and ordering for the first location. Extra branches that already exist are **not deleted or deactivated**, and their menu availability and orders are untouched; they simply are not offered to customers. A customer who selected another branch earlier can still finish an order there until they pick again.
- **When it comes back on:** all active branches are offered again.
- **Depends on:** nothing.

### `push` (remote push notifications)
- **Covers:** remote order-status pushes (FCM/APNs). `PushNotificationService` sends nothing while the module is off; in the customer app, push registration is not started and the notifications switch on Profile is hidden.
- **Not an endpoint gate:** `POST /api/v1/auth/device-tokens` keeps accepting tokens (it never returns `module_disabled`), so devices that registered earlier, or an older app build, are not broken and pushes resume as soon as the module is back on. The module is an on/off for *sending*.
- **Keeps working:** order updates for an open app over SignalR and the in-app/local notifications (core), and all ordering.
- **Depends on:** nothing. Firebase credentials are still configured separately (`Firebase:Enabled`); the module is the commercial switch on top.

### `loyalty` (bonus points: earn, spend, hold, balance, history)
- **Covers:** `LoyaltyService` new activity: balance, offsite history, earning on completion, and placing a new hold when a customer pays with bonuses. In the customer app the bonus balance on Profile, the bonuses tile on News and the "pay with bonuses" row in the cart; in the admin app the customer's bonus balance and the bonuses column.
- **How it switches off:** like `Loyalty` being unconfigured, the API answers `enabled: false` instead of an error (the apps already hide everything for `enabled: false`, and `GET /loyalty/*` is read in the background, so a 403 would only produce noise). It is a second switch on top of `Iiko:Enabled`; both must be on.
- **Background jobs:** the loyalty retry job checks the gate and does nothing while the module is off (done in Phase 1). Nothing is deleted.
- **Never strands points:** finalising or releasing a hold that already exists ignores the module, so switching it off mid-order cannot leave points reserved in iiko.
- **When it comes back on:** completed orders that earned nothing while the module was off are picked up by the existing safety-net sweep and credited, so customers are not penalised for the gap.
- **Existing data:** points spent/earned on past orders still show on those orders.
- **Depends on:** iiko adapter or, later, `own_pos` (see Phase 6); the dependency check is a warning only.

### `iiko_sync` (optional iiko adapter, no new features)
- **Covers:** pushing new accepted orders to iiko (`IikoOrderSyncService.PushOrderAsync`), the iiko webhook (`/webhooks/iiko`) and the admin lookups (`/admin/iiko/*`: nomenclature, payment types, terminal groups, webhook registration). In the admin app the iiko product mapping on menu items, the terminal group on branches and the "Synced to iiko" badge on live orders are hidden.
- **How it switches off:** `403 {code:"module_disabled"}` on the endpoints; new orders are simply not pushed (they stay `NotPushed`). It is a second switch on top of `Iiko:Enabled` and `Iiko:PushOrdersEnabled`.
- **Background jobs:** the push retry job checks the gate (done in Phase 1).
- **Never leaves orders open:** closing an order that was already pushed ignores the module.
- **Existing data:** iiko ids on menu items and branches stay in the database, so switching the module back on needs no re-mapping.
- **Not covered:** loyalty talks to iiko too, but it has its own `loyalty` module.
- **Depends on:** nothing; replaced by `own_pos` in Phase 6.

### `online_payments` (pay online by card, Apple Pay or Google Pay through Stripe)
- **Covers:** opening a new online payment page (`POST /payments/create`) and showing "Pay online" in the customer cart and on the order page.
- **How it switches off:** `POST /payments/create` returns `403 {code:"module_disabled"}`; `GET /payments/config` answers with no provider (same as "not set up") so the app hides "Pay online" on its own.
- **Never strands a payment:** payment status, the Stripe webhook and refunds ignore the module, so a payment that already started still finishes, and money can still be given back.
- **Keeps working:** the Kaspi / Halyk / Freedom bank choices in the cart are labels for paying at the counter (staff mark the order paid), so they stay in core.
- **Depends on:** nothing. The provider is chosen and its keys stored per cafe (Platform → Online payments, `Stripe:SecretKey`, `Stripe:WebhookSecret`); see `docs/stripe-payments.md`.

### `verification` (phone verification code at sign-up and phone change)
- **Covers:** the one-time code sent when a customer registers or changes their phone number (`AuthService`). Verification is required only when `Otp:Required` is on **and** the module is licensed.
- **How it switches off:** the same path as `Otp:Required=false`: registration creates the account immediately and returns the tokens (`verificationRequired: false`), and a phone change is applied immediately. Both apps already follow `verificationRequired`, so no UI change was needed. Nothing returns `module_disabled`, because sign-up is core.
- **Caveat:** without verification anyone can register with any phone number, and loyalty is linked by phone, so a cafe running `loyalty` without `verification` can have bonus balances claimed by someone else's number. Show this in the commercial terms; the platform does not block the combination.
- **Never strands a sign-up:** confirming a code that was already sent (`register/verify`, `me/phone/verify`) ignores the module.
- **Depends on:** nothing technically; commercially pairs with `loyalty`. The WhatsApp / SMS provider is still configured separately (`Otp:Enabled`).

### `branding` (white-label brand)
- **Covers:** the saved brand (name, primary and accent colour, logo, optional dark mode logo, app icon and splash image URLs (all https), welcome line, up to 6 links, support contact) in `GET /api/v1/app/config`. The apps turn the primary colour into the `--brand-*` scale and cache it, so a returning customer sees the cafe's colours on the first paint.
- **How it switches off:** the config serves the Yurt default brand and the saved brand is kept, so switching the module back on restores it. The platform operator can still edit the brand while it is off (`GET`/`PUT /api/v1/platform/brand`, SuperAdmin only).
- **Admin screen:** the Brand section on the Platform page (SuperAdmin) edits these values with a live preview.
- **Accent scale:** gradient ends and soft tints use `accent-50/400/500`, generated from the accent colour (defaults are the orange the gradients always had).
- **Readability tokens:** `--brand-hero-text` (text on gradient headers), `--brand-ink` (brand-coloured text on light pages) and `--brand-on-dark` are computed from the primary colour; for the Yurt default they keep the old look.
- **Readability:** text on the primary colour follows `--brand-on-primary`, and near-black buttons use `--brand-on-dark` (the primary lightened until it reads on near-black). The Brand screen warns about a primary that is too light or too dark.
- **Font:** a preset (`font`: Inter, system or serif, no download) and an optional own font file (`fontUrl`: an https link ending in .woff2, .woff, .ttf or .otf). The apps register the file as an `@font-face` with `font-display: swap` and put it first in `--brand-font`, so the preset shows while it loads and stays if it fails. The file's host must send CORS headers (`Access-Control-Allow-Origin`), or browsers refuse the font.
- **Dark mode logo:** shown instead of the logo while the app is in dark mode; empty means the normal logo is used.
- **Depends on:** nothing.

### `table_ordering` (order by QR at the table)
- **Covers:** the Tables page in the admin app (`/api/v1/admin/tables`: add tables to a branch, rename, new QR code, delete) and the public `GET /api/v1/tables/{code}` the customer app calls after a scan.
- **How it works:** each table has a random 10-character code. Its QR code opens `<customer app>/t/<code>`, which picks the branch and remembers the table on the phone for 4 hours (or until the guest picks another branch or presses "Pick up instead"). The cart shows "To table 5", and `POST /orders` takes a `tableCode`. The order keeps the table name (`tableLabel`), shown on live orders, the kitchen screen, printed tickets and receipts, and the guest's order screen (no 2GIS route for a table order).
- **QR address:** the cafe's own web address (Platform page), otherwise `Payment__CustomerAppUrl` on the server. Without either the page shows the tables but no QR codes.
- **Printing:** "Print all QR codes" prints an A4 sheet, two cards per row (cafe name, QR code, table name). "New QR code" makes the old sticker stop working.
- **When off:** both endpoints return `403 module_disabled`, the Tables page and link are hidden, the cart shows no table, and an order sent with a `tableCode` becomes an ordinary pickup order.
- **Existing data:** tables and the table names on past orders stay and show again when the module is back on. Deleting a table keeps its orders' table name.
- **Depends on:** nothing.

### `own_pos` (self-developed POS, shipped one feature at a time)
Gated so far: the **Kitchen** screen, **Cashier**, **Stock** and **Printers**. Other `own_pos` features are added here as they ship.
- **Kitchen screen:** admin route `/kitchen` and menu entry. A tablet page per branch with three columns (New, Preparing, Ready) of the accepted orders, oldest first, with items, toppings, notes and the wait time (red when past the promised minutes). One big button per card moves it on (Start, Ready, Handed over). It uses the same order API and live events as Live Orders, so no backend gate is needed and nothing changes for customers.
- **When off:** the route redirects to Orders and the menu entry is hidden. Live Orders keeps working.
- **Depends on:** nothing. It works next to iiko; orders still go to iiko as before while the cafe uses it.
- **Stations:** the **Stations** button on the kitchen screen opens a setup panel to add stations (for example Kitchen and Bar, up to 10) and choose a station for each menu category (`GET admin/stations/routing`, `POST admin/stations`, `DELETE admin/stations/{id}`, `PUT admin/stations/categories/{categoryId}`, gated by `own_pos`). Once stations exist, tabs appear on the kitchen screen: **All** or one station. A screen set to one station shows only the items made there, and an order with none of its items there is left out. Categories with no station show on every screen so nothing is missed. The choice is remembered per tablet. Deleting a station only un-routes its categories.
- **Ready per station:** on a screen set to one station, the **Ready** button of an order that has items made there becomes **Our part is ready** (`POST admin/orders/{id}/stations/{stationId}/ready`, `DELETE` to undo while the order is still being made, gated by `own_pos`; stored in `OrderStationReadies`). Cards with items for more than one station show a small chip per station (✓ when that part is done). When every station that has items in the order is ready, the order moves to **Ready** by itself and the customer is told as usual. If the order also has items whose category has no station, nobody owns those, so the order does not move by itself and staff press **Ready** on the **All** screen as before. The **All** screen keeps the whole-order buttons, so a cafe without stations works exactly as before.
- **Kitchen ticket:** each kitchen card has a **Print ticket** button. It prints a narrow 80 mm slip through the browser (order number, station, time, customer, the items to make with sizes, toppings and notes, no prices). With a station chosen it lists only that station's items. No backend change.
- **Network printers:** admin route `/printers` and menu entry (gated by `own_pos`). Each branch can have kitchen printers and receipt printers that the server prints to directly with ESC/POS over TCP (raw port printing, port 9100 to 9109 only, so the address can never point the server at its database or other services). A kitchen printer is tied to one station (it gets that station's items plus items with no station, the same as the station's screen) or to no station (every item). Settings per printer: branch, name, address, port, paper width (32 characters for 58 mm, 42 or 48 for 80 mm), language on paper (ru, kk, en), the character table number for Cyrillic (code page 866, `17` on most printers; Kazakh letters print as the nearest Russian ones) and **Print by itself when an order is accepted**. `GET/POST admin/printers`, `PUT/DELETE admin/printers/{id}` (adding, changing and deleting need the Admin role), `POST admin/printers/{id}/test` prints a test page right away and answers `502` with the reason when the printer does not answer. `GET admin/printers/jobs?limit=` lists the latest jobs with their state (Waiting, Printed, Not printed with the reason); the page refreshes it every 10 seconds.
  - **When it prints:** accepting an order queues a ticket on every kitchen printer of the branch that has items for it and a receipt on every receipt printer, but only on printers set to print by themselves. The **Print ticket** button on the kitchen screen (`POST admin/orders/{id}/print/ticket?stationId=`) and **Print receipt** in Orders (`POST admin/orders/{id}/print/receipt`) send to the printers; when the branch has no printer for it (the answer says `printers: 0`) or the call fails, they print through the browser as before.
  - **How it sends:** jobs are stored in `PrintJobs` with the bytes already made, and a background sender sends them at once (and every 15 seconds for retries). A job is tried 3 times, then marked not printed; a job still waiting after 15 minutes is dropped so the kitchen does not get an old ticket much later. Finished jobs are deleted after 7 days. Printing never blocks or fails an order.
  - **Network:** the server opens the connection to the printer, so it must be able to reach the printer's address. That works when the server runs in the cafe or reaches the cafe's network (VPN). For a server in the cloud, tick **Through the print agent in the cafe** on the printer and run the print agent in the cafe (below).
  - **Print agent:** `scripts/print-agent.mjs` (Node.js 18+, no packages) runs on a computer in the cafe and asks for the branch's jobs every 3 seconds. Setup steps for staff: `docs/print-agent.md`. Each branch has at most one agent key (`PrintAgents` table, only a SHA-256 hash is kept); the key starts with the cafe's short name and a dot so the agent can send `X-Tenant`. Admin: **Make key** / **New key** (`POST admin/printers/agents/{locationId}`, Admin role, the key is shown once and an older key stops working), **Delete** (`DELETE …`), and the branch shows whether the agent asked in the last minute (`GET admin/printers/agents`). Agent API (no login, the key goes in `X-Print-Agent-Key`, gated by `own_pos`): `POST print-agent/jobs/claim` hands over up to 10 waiting jobs of the branch's agent printers (host, port, bytes in base64) and marks them as being sent; `POST print-agent/jobs/{id}/result` with `{ ok, error }` marks a job printed, or puts it back until its 3 tries are used. The server's own sender skips agent printers. A test print on an agent printer is queued and shows in the job list.
  - **Not fiscal:** the printed receipt is an order slip, not a fiscal receipt from an online cash register (OFD). When the order's official tax receipt already went out, the slip gets a QR code linking to it (see Official tax receipts below).
- **Cash drawer:** a cash drawer plugs into the receipt printer (the RJ11/RJ12 "DK" socket on the back). Tick **A cash drawer is plugged into this printer** on a receipt printer (kitchen printers cannot have one). The drawer then opens by itself when an order paid in cash is marked **Paid**, and when a split payment with a cash part is saved; card and Kaspi payments leave it shut. The **Open drawer** button on the Cashier page opens it any time (for change, cash in/out, counting); any staff member can press it, and each press is written to the audit log. The test print also opens it, so the cable can be checked while setting up. Nothing is printed: the server sends only the ESC/POS "pulse" command (`ESC p`, to both drawer pins). It goes through the same print queue, so it also works through the print agent, but a drawer that could not open within 1 minute stays shut (it is not opened later when nobody may be at the till). The job list shows it as kind `Drawer`.
- **Bluetooth printers:** tick **Bluetooth, through a tablet in the cafe** on a printer (`Printers.ViaBluetooth`, off by default; such a printer has no address and the agent tick is ignored). The admin app on a tablet next to the printer connects to it with the browser's own Web Bluetooth (Chrome on Android, Windows, macOS, ChromeOS; not Safari on iPad/iPhone) and only Bluetooth Low Energy printers show up; printers that only speak classic Bluetooth do not. **Connect this tablet** on the Printers page pairs the printer entry with a device; the tablet remembers it and reconnects after a reload where Chrome allows it. While the admin app is open (any page, any signed-in staff member), the tablet asks every 3 seconds for the jobs of the printers connected to it: `POST admin/printers/bluetooth/claim` with `{ printerIds }` hands over up to 10 waiting jobs of those printers (bytes in base64) and marks them as being sent; `POST admin/printers/bluetooth/jobs/{id}/result` with `{ ok, error }` works like the agent's. The server's own sender and the print agent skip Bluetooth printers. Bytes go out in 100-byte writes to the first writable characteristic of a known printer service (`000018f0-…`, `e7810a71-…`, ISSC `49535343-…`, Nordic UART). Logic in `yurt-admin/src/app/core/bluetooth/` with tests against a pretend printer (`ng test yurt-admin`). Staff steps: `docs/bluetooth-printers.md`. **Not tried on a real printer yet.**
- **Not done yet (printers):** classic (non-BLE) Bluetooth printers and iPad, which need the admin app wrapped as a native app with a Bluetooth plugin.

#### Stock and the automatic stop-list (per product, per branch)
- **Covers:** `GET /api/v1/admin/stock?locationId=` and `PUT /api/v1/admin/stock/{menuItemId}/{locationId}` (body `{ quantity, lowStockAt }`; a null `quantity` stops counting the item); the admin **Stock** page and menu entry.
- **How it works:** an item with a count is limited to what is left in that branch. An order for more than is left is refused with a plain message ("Only 2 left of ..." or "... is sold out"). Accepting an order lowers the count (never below zero, safe when two orders are accepted together). At zero the item disappears from that branch's customer menu by itself; setting a number again or clearing the count brings it back. Items without a count are unlimited, as before. The admin list marks items at or below their warning number as running low.
- **When off:** the Stock endpoints return `403 module_disabled`, the page redirects to Orders and the menu entry is hidden. Counts are **not enforced** while the module is off (menu and orders ignore them), so nothing can stay stuck at zero without a way to fix it. The counts are kept and apply again when the module is back on.
- **Low-stock alerts:** `GET /api/v1/admin/stock/alerts?locationId=` (no branch means all branches) lists dishes and ingredients that are out or at/under their warn-at number, out first, up to 100. The admin shows a red number badge on the **Stock** menu entry (refreshed every 2 minutes) and a "Needs attention" summary on the Stock page for the chosen branch. While `own_pos` is off the list is empty.
- **Restocking history:** `GET /api/v1/admin/stock/history?locationId=&take=` (newest first, default 100, up to 500) lists every hand change to a dish or ingredient count at the branch: the item, the count before and after (null means not counted), the difference, who made it and when. It is shown on the **History** tab of the Stock page. A row is written whenever a count is set or cleared through the Stock or Ingredients endpoints; changing only the warn-at number writes nothing. Orders lowering counts are not listed (they are in the order history). Rows keep the item's name, so they still read after the item is deleted. Table `StockChanges` (additive).
- **Phone alerts:** the Stock page has a **Phone alerts** box with up to 5 phone numbers (`GET`/`PUT /api/v1/admin/stock/alert-phones`; everyone on staff can see it, only an admin can change it; saved per cafe as the `stock.alert-phones` setting, no new table). When an accepted order takes a dish or ingredient from above its warn-at number to at or under it, or to zero, every cafe-app account signed in with one of those numbers gets one push (Russian text like the order pushes, for example "Мало на складе — Milk: осталось 150 ml (Main)"). Only the order that crosses the line alerts; later orders stay quiet until someone restocks. Numbers typed as +7…, 7… or 8… all match. Each number shows whether it can get alerts yet (an account with that number has the app with notifications on). Uses the cafe's own Firebase setup, so it needs `push` on and Firebase set up; with either off, nothing is sent and orders are never affected.

#### Cashier, shifts and the Z report (per branch)
- **Covers:** `GET shifts/current?locationId=` (empty body when none is open), `GET shifts?locationId=`, `POST shifts/open` (`{ locationId, openingCash }`), `POST shifts/{id}/cash` (`{ amount, isOut, reason }`), `POST shifts/{id}/close` (`{ countedCash, note }`, returns the Z report), `GET shifts/{id}/report`, all under `/api/v1/admin/`. The admin **Cashier** page and menu entry. Workers can use it, not only admins.
- **How it works:** one open shift per branch (the database enforces it). The report counts the orders completed at that branch between opening and closing: orders, declined, before discounts, discounts, points spent, takings in money (total minus points), takings by payment method. The drawer should hold: opening cash + cash sales + cash put in − cash taken out; closing with the cash counted shows the difference. While the shift is open the same numbers are the X report. Orders with no payment method recorded count as cash. The Z report can be printed from the browser.
- **When off:** endpoints return `403 module_disabled`, the page redirects to Orders and the menu entry is hidden. Shifts are kept.
- **Receipts:** the order details in Orders have a **Print receipt** button (only while `own_pos` is on). It prints a narrow 80 mm receipt (cafe name, branch, date, short order number, items with sizes and toppings, discount, points, total, payment method) through the browser print dialog, so any printer the computer can print to works. It is built in the browser from the order already on screen; there is no backend change.
- **Split payments:** the payment box of an order has a **Split payment** link (only while `own_pos` is on). The cashier lists up to 5 parts, each with a method and an amount; the parts must add up to what the guest pays in money (total minus points), else `400`. `GET/PUT admin/orders/{id}/split-payment` (gated by `own_pos`). Saving replaces earlier parts, marks the order paid and keeps the biggest part as the order's main method. The Z report counts each part under its own method, so cash sales and the cash that should be in the drawer only include the cash part. Other reports (Analytics) still show the one main method. The printed receipt lists each part when an order has two or more.
- **Payment methods per branch:** the branch dialog (Locations) has a **Payment methods** group of tick boxes (only while `own_pos` is on). Tick none to offer every method (the default). The customer app shows only the ticked methods at checkout (`paymentMethods` on the location), and the server refuses an order with another method (`422`). `Other` (used by group orders) is always accepted, and the check is skipped while `own_pos` is off. Cash is not shown in the customer app anyway; ticking it only matters for the cashier. Saving a location without the field leaves the setting as it was.
- **Not done yet:** fiscal receipts (online cash register). Direct printing to network printers is described under Kitchen above.

#### Official tax receipts (cloud cash register, per cafe)
- **What it is:** every sale must get an official tax receipt from a registered online cash register (see `docs/fiscal-receipts-kz.md`). Yurt does not become a cash register; it sends each sale to the cafe's **cloud cash register** through an adapter behind `IFiscalRegistrar`. There are two adapters: **Webkassa** and **ReKassa**; each cafe picks one (or none).
- **Off by default.** It runs only for a cafe whose provider is set **and** while `own_pos` is on. Turn it on only on the day the cafe leaves iiko (or its old register), so no sale gets two receipts; only orders placed after it was turned on get receipts.
- **Settings (Platform page, Official tax receipts, picks the cafe with `X-Tenant`):** `GET/PUT /api/v1/platform/fiscal` with `{ provider: "webkassa" | "rekassa" | null, skipMethods: ["KaspiBank", ...], vatPercent: 16 | null, branches: [{ locationId, registerNumber }] }`. Saved on the cafe (`Tenant.FiscalProvider`, `FiscalSince`, `FiscalSkipMethods`, `FiscalVatPercent`) and the branch (`Location.FiscalRegisterNumber`, the Webkassa cashbox number or the ReKassa register serial number). Leaving `branches` out keeps the numbers. The provider login goes in the cafe's encrypted **Secrets**: `Fiscal:Login`, `Fiscal:Password`, `Fiscal:ApiKey` (partner key). Server setting `Webkassa__BaseUrl` (default the live server `https://kkm.webkassa.kz`; use `https://devkkm.webkassa.kz` with a test account).
- **ReKassa differences:** there is no cafe-wide login. Each register logs in by itself with its serial number (ЗНМ, typed as the branch's register number) and the "password for third-party apps" made in the ReKassa cabinet (secret `Fiscal:Password`). `Fiscal:Login` is not used. Closing the shift (fiscal Z report) also needs the register PIN (secret `Fiscal:Pin`); without it the Z report fails with a clear message and the cashier can try again later. Yurt's partner key at ReKassa is the server setting `ReKassa__ApiKey`; a cafe's own `Fiscal:ApiKey` secret wins over it. Server setting `ReKassa__BaseUrl` (default `https://app.rekassa.kz`; use ReKassa's test server with a test account). The adapter logs in, finds the register's id by its serial number, then sends tickets to it; a repeated ticket carries the same `X-Request-ID` so a lost answer should not make a second receipt.
- **When a receipt is made:** a background job runs every minute per cafe. A paid order that the cafe took on (Accepted, Preparing, Ready or Completed) gets one **sale** receipt; orders still waiting to be accepted or declined get none. A refunded order whose sale receipt went out gets one **return** receipt. Lines are the order lines; the order discount and bonus points are spread over the lines, so the receipt total is what the guest paid in money. Payments are the split parts, or the one method. Stored in `FiscalReceipts` (one sale and one return per order at most, the database enforces it).
- **Skipped on purpose:** an order paid only with skipped methods (for example Kaspi while Kaspi Kassa makes the Kaspi receipts), or paid fully with points. It shows as "No tax receipt (skipped)". An order paid partly with a skipped method still gets a full receipt for now (open question: check with the cafe's accountant whether the Kaspi part should be left off).
- **Never blocks a sale.** If the provider is down, the login is missing or the branch has no register number, the receipt stays **Pending** and is tried again after 1, 2, 4 ... minutes, at most every 30 minutes, without giving up. Staff see a **Not fiscalized** badge on the order (Orders list and details) and the list on the Cashier page with the reason and a **Try again** button (`GET admin/fiscal/waiting?locationId=`, `GET admin/fiscal/orders/{orderId}`, `POST admin/fiscal/receipts/{id}/retry`, gated by `own_pos`). A sent receipt shows a link to the receipt (the provider's ticket page).
- **Shift close:** closing a Yurt shift also closes the fiscal shift of the branch's register (fiscal Z report). While receipts of that branch are still waiting, closing answers `409` and the Cashier page asks "close anyway?" (`closeWithWaitingReceipts: true`). A failed fiscal Z report never undoes the close; it is shown on the Z report with **Try again** (`POST admin/shifts/{id}/fiscal-z-report`).
- **Receipt link for the guest and on paper:** once a sale receipt went through and the provider gave a link to it (`FiscalReceipt.TicketUrl`), the customer app's order screen shows a **Tax receipt** button that opens it (and **Refund tax receipt** for a sent return receipt). The links come in `fiscalReceiptUrl` / `fiscalReturnUrl` of `GET /api/v1/orders/{id}` (customer, only while `own_pos` is on); live order updates do not carry them, so the screen asks for the order again on the next update until the link is there. A receipt printed on a network receipt printer after that also gets a **QR code** with the link at the bottom (drawn by the printer itself with the ESC/POS `GS ( k` commands, so no image is sent), plus the receipt number. Only `http`/`https` links are ever shown or printed. Nothing changes for an order without a sent receipt. Note: the receipt printed by itself on accept usually comes out **before** the tax receipt is sent (the job runs every minute), so it has no QR code; press **Print receipt** in Orders to print one with it, or let the printer do it by itself (next point).
- **Print again with the tax QR code (optional, per receipt printer, off by default):** tick **Print the receipt again with the tax receipt QR code** on a receipt printer (`Printer.ReprintWithTaxQr`; kitchen printers cannot have it). As soon as an order's sale tax receipt is sent (by the background job or by **Try again**), the receipt is queued once more on the printers of that branch that have the tick, now with the QR code. It only happens for a receipt with an `http`/`https` link that was queued at most 15 minutes before it went through; when the cash register service was down for longer, the guest has usually left, so nothing prints by itself (staff can still press **Print receipt**). A return receipt never prints anything. A failed print never affects the tax receipt.
- **QR code on the browser-printed receipt:** when the branch has no receipt printer, **Print receipt** in Orders prints through the browser; that receipt now also gets the tax receipt number and QR code at the bottom once the sale receipt went through. The QR picture is drawn on the server (`ticketQr` in `GET admin/fiscal/orders/{orderId}`, an SVG `data:` link made with QRCoder from the `http`/`https` link only), so the admin app needs no extra library. If the tax receipts cannot be loaded, the receipt prints without the QR code as before.
- **Not verified yet:** the exact Webkassa calls. The adapter follows Webkassa's known partner flow (`api/Authorize`, `api/Check`, `api/ZReport`, `X-API-KEY` header, operation, payment and tax type codes); every guess is marked "unverified" in `WebkassaFiscalRegistrar`. Check them against the partner documentation and a test account before the first cafe goes live. The same is true for **ReKassa** (`api/auth/login`, `api/crs`, `api/crs/{id}/tickets`, `api/crs/{id}/shifts/close`, field names, money as tenge plus tiyn, the `X-Request-ID` header); every guess is marked "unverified" in `ReKassaFiscalRegistrar`.

#### Ingredients and recipes (per ingredient, per branch)
- **Covers:** `GET/POST /api/v1/admin/ingredients`, `PUT/DELETE .../{id}`, `PUT .../{id}/stock/{locationId}` (null `quantity` stops counting), `GET/PUT .../recipes/{menuItemId}` (saving replaces the whole recipe). The **Ingredients** and **Recipes** tabs on the Stock page.
- **How it works:** a recipe line says how much of an ingredient one portion uses, for every size or one size. A dish leaves the customer menu when an every-size line needs more than the branch has. An order is refused when any line (size-specific ones included) cannot be covered. Accepting an order lowers the ingredient counts, never below zero.
- **When off:** same as Stock: endpoints return `403 module_disabled`, counts are not enforced.
- **Toppings:** a topping can use ingredients too (`GET/PUT /api/v1/admin/ingredients/toppings/{toppingId}`, set on the Recipes tab by picking a topping). Each time a guest adds the topping to an item, that amount is used once per portion ordered. A topping leaves a branch's customer menu when an ingredient it uses is short there, an order with it is refused when the amount cannot be covered, and accepting the order lowers the ingredient. A topping with no ingredient is not counted.

## Limited mode (cafe stopped paying)

Not a module: it applies to the whole cafe, on top of the module gates.
- **When:** the operator ticks **Limit this cafe now** in /platform (`Tenant.LimitedByOperator`), or the cafe's
  `Tenant.PaidUntil` is more than `Billing:GraceDays` days ago (default 7). `PaidUntil` null means payment is not
  tracked and the cafe is never limited by date. Between `PaidUntil` and the end of the grace days the cafe works
  normally and its admins see a "payment is late" warning on the Subscription page.
- **What stops:** placing an order (`POST /api/v1/orders`) and starting, joining, filling or checking out a group
  order. These answer `403 { code: "cafe_limited", title }` (`[BlockWhenCafeLimited]`, `Yurt.WebApi/Common`). The
  customer app reads `ordering.paused` from `/api/v1/app/config` and shows a "Ordering is paused" popup instead of
  adding to the cart or checking out.
- **What keeps working:** sign-in for customers and staff, menus, order history and active orders, bonuses, paying
  for or cancelling an order placed before, and the whole admin app (staff see a red banner).
- **Who sets it:** `GET/PUT /api/v1/platform/access` (SuperAdmin, for the chosen cafe; body
  `{ paidUntil, limitedByOperator }`), shown as the **Limited mode** card on the Platform page. Billing only needs to
  set `Tenant.PaidUntil` and call `ITenantDirectory.Invalidate()`; nothing here knows how a payment is detected.
- **Fail-open:** if the cafe list cannot be read, the cafe counts as paid up. Changes apply within the cafe list cache
  (60 s) or at once when made through /platform.
